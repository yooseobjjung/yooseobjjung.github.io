ENTERPRISE AI WORKFLOW · NOTION-NATIVE DESIGN

Enterprise AI Knowledge & Request Management

A governed operating layer for internal requests, knowledge, and AI-assisted triage
Notion workspace designNotion API architecture AI agent designHuman-in-the-loopRBAC
Problem / customer discovery

Imagine a Korean enterprise where employee requests are scattered across chat, email, and undocumented team processes. People cannot find the right policy, requests lack clear owners, and sensitive cases are escalated inconsistently. The goal is to make Notion the operating layer for knowledge and request tracking, while preserving external systems of record and human approval for consequential actions.

Solution & architectural decisions
  • Discovery: map request categories, existing systems, current pain points, stakeholder roles, SLAs, and adoption barriers; define future-state workflow and success criteria.
  • Notion data model: Requests, Knowledge Articles, Teams, and Decisions databases with relations, ownership, lifecycle status, and source-of-truth rules.
  • AI-assisted triage: proposed agent classifies intent, retrieves approved knowledge, drafts a grounded response, and recommends an owner; unsupported or high-risk actions require human review.
  • Governance: role-based workspace permissions, least-privilege integration tokens, restricted knowledge access, audit events, and explicit approval gates.
  • Integration boundary: use Notion for collaboration and task state; retain HR, ticketing, and identity systems as authoritative sources where needed, connecting via supported APIs.
  • Launch & adoption: propose pilot champions, phased rollout, operating runbooks, and measures for cycle time, deflection, usage, and escalation quality.

    CASE 01
    LinguaSort
    Multilingual LLM classification + evaluation harness
    PythonGPT-4oGemini structured outputeval harnessCI gate
    Problem

    A consumer app routes support and review text written in English, Korean, Japanese, and Chinese into issue categories. The rules-based router quietly misclassified CJK text, sending complaints to the wrong queues. I needed an LLM classifier and an evaluation harness that measures accuracy per language and blocks regressions before release.

    Approach
    • Called GPT-4o / Gemini with JSON-schema structured output to tag each message with intent + severity.
    • Built a 1,200-item human-labeled golden set, stratified by language, as ground truth.
    • Ran per-language accuracy + confusion analysis: CJK trailed EN by ~14 pts — the few-shot exemplars were English-centric and honorifics broke intent detection.
    • Fixed with language-adaptive exemplars + a script-detection pre-router; added a CI gate that fails the build if any language drops >2 pts.
    ▹ classify.py — structured classification + per-language eval+ 
    from pydantic import BaseModel
from enum import Enum
import anthropic, json, collections

class Intent(str, Enum):
    BILLING = "billing"; BUG = "bug"; REFUND = "refund"
    HOW_TO = "how_to"; PRAISE = "praise"; OTHER = "other"

class Label(BaseModel):
    intent: Intent
    severity: int          # 1..5
    is_cjk: bool

SCHEMA = Label.model_json_schema()

def classify(text: str, exemplars: list[dict]) -> Label:
    """Language-adaptive few-shot -> strict JSON label."""
    shots = "\n".join(f"[{e['lang']}] {e['text']} -> {e['label']}"
                      for e in exemplars)
    prompt = (f"Classify the message. Return ONLY JSON "
              f"matching this schema:\n{json.dumps(SCHEMA)}\n\n"
              f"Examples:\n{shots}\n\nMessage: {text}")
    raw = call_model(prompt)                 # GPT-4o / Gemini wrapper
    return Label(**json.loads(strip_fences(raw)))

def eval_by_language(gold: list[dict], exemplars_for) -> dict:
    hits = collections.Counter(); tot = collections.Counter()
    for row in gold:
        pred = classify(row["text"], exemplars_for(row["lang"]))
        tot[row["lang"]] += 1
        hits[row["lang"]] += int(pred.intent == row["intent"])
    return {lang: round(hits[lang] / tot[lang], 3) for lang in tot}

# CI gate: block deploy on any per-language regression > 2pts
def gate(curr: dict, baseline: dict, tol: float = 0.02) -> bool:
    drops = {l: baseline[l] - curr[l] for l in curr
             if baseline[l] - curr[l] > tol}
    assert not drops, f"Accuracy regression: {drops}"
    return True

    CASE 02
    ReadmitLens
    30-day hospital readmission risk on an open dataset
    Pythonpandasscikit-learn gradient boostinggrouped CVcalibration
    Problem

    Which diabetic inpatients are most likely to return within 30 days — and where is the rate anomalously high? Built on the public UCI "Diabetes 130-US hospitals" dataset (~101k encounters) so the methodology is fully reproducible.

    Approach
    • Cleaned + encoded encounters; engineered features from prior inpatient visits, diagnosis count, A1C result, and discharge disposition.
    • Trained gradient-boosted trees with patient-grouped cross-validation to prevent the same patient leaking across folds.
    • Calibrated probabilities (isotonic) so a "30% risk" score means what it says — critical for triage thresholds.
    • Subgroup scan surfaced an elevated readmission rate for emergency admissions discharged to short-term care.
    ▹ readmit_model.py — leakage-safe training + calibration+ 
    import pandas as pd
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.calibration import CalibratedClassifierCV
from sklearn.model_selection import StratifiedGroupKFold, cross_val_predict
from sklearn.metrics import roc_auc_score

df = load_uci_diabetes()                     # ~101k encounters
df["y"] = (df["readmitted"] == "<30").astype(int)

FEATURES = ["num_inpatient_prior", "num_diagnoses", "num_medications",
            "a1c_result", "discharge_disposition", "admission_type",
            "time_in_hospital", "age_bucket"]
X, y = encode(df[FEATURES]), df["y"]
groups = df["patient_nbr"]                    # keep a patient in one fold

base = HistGradientBoostingClassifier(
    learning_rate=0.06, max_depth=4, l2_regularization=1.0)
model = CalibratedClassifierCV(base, method="isotonic", cv=3)

# grouped CV so a patient never spans train/test
cv = StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=7)
proba = cross_val_predict(model, X, y, groups=groups,
                          cv=cv, method="predict_proba")[:, 1]

print("ROC-AUC:", round(roc_auc_score(y, proba), 3))   # -> 0.681
df["risk"] = proba
top_decile = df[df.risk >= df.risk.quantile(0.90)]
print("share of readmits captured:", round(top_decile.y.mean() /
                                           df.y.mean(), 2), "x lift")
    Honest ceiling: this dataset tops out around 0.68 AUC — the value is in ranking + calibration for triage, not a heroic score.

    CASE 03
    CohortIQ
    Retention & acquisition-channel attribution
    SQLBigQuerycohort analysis LTV:CACPython
    Problem

    A freemium app was optimizing for cheap installs. The real question: which acquisition channels produce durable users? Built on a synthetic event log generated to mimic realistic retention decay across channels.

    Approach
    • Cohorted signups by week × channel in SQL; computed week-N retention and a contribution-margin LTV per channel.
    • Referral cohorts retained far better and had lower CAC — the opposite of how spend was allocated.
    • Modeled a budget shift from paid social into referral incentives at flat total spend.
    ▹ retention.sql — weekly cohort retention by channel+ 
    -- Week-N retention curve per acquisition channel
WITH first_seen AS (
  SELECT user_id,
         channel,
         DATE_TRUNC(MIN(event_date), WEEK) AS cohort_week
  FROM events
  GROUP BY user_id, channel
),
activity AS (
  SELECT f.channel,
         f.cohort_week,
         DATE_DIFF(DATE_TRUNC(e.event_date, WEEK),
                   f.cohort_week, WEEK) AS week_n,
         COUNT(DISTINCT e.user_id) AS actives
  FROM first_seen f
  JOIN events e USING (user_id)
  GROUP BY 1, 2, 3
),
base AS (
  SELECT channel, cohort_week, actives AS cohort_size
  FROM activity WHERE week_n = 0
)
SELECT a.channel,
       a.week_n,
       ROUND(SUM(a.actives) / SUM(b.cohort_size), 3) AS retention
FROM activity a
JOIN base b USING (channel, cohort_week)
GROUP BY 1, 2
ORDER BY a.channel, a.week_n;

    CASE 04
    PipeGuard
    Automated reporting pipeline with data-quality gates
    dbtSQLdata quality orchestrationalerting
    Problem

    A weekly ops report was hand-assembled from five sources every Monday, and silent data errors regularly slipped through undetected. The goal: make it trustworthy and near-automatic.

    Approach
    • Modeled the five sources in dbt with a clean staging → marts layering.
    • Added schema, freshness, uniqueness, and accepted-values tests that fail the run before bad data reaches the report.
    • Scheduled runs with a fail-fast alert, replacing the manual spreadsheet stitch with a one-glance review.
    ▹ schema.yml — dbt tests as the quality gate+ 
    version: 2

models:
  - name: stg_orders
    description: "Cleaned orders, one row per order_id."
    columns:
      - name: order_id
        tests: [unique, not_null]
      - name: status
        tests:
          - accepted_values:
              values: ['placed','shipped','returned','cancelled']
      - name: amount
        tests:
          - dbt_utils.accepted_range:
              min_value: 0
              inclusive: true

    # block the whole run if source data is stale
    freshness:
      warn_after: {count: 12, period: hour}
      error_after: {count: 24, period: hour}
    loaded_at_field: _ingested_at
